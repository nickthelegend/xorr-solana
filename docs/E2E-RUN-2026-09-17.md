## 1. Fund — PARTIAL

`tools/prove-solana-deposit-withdraw.ts` passes every assertion it makes, and they are real ones:
the config endpoint is strictly sandbox, the target token is `usdc_sol`, the URL carries the user's
own Solana address and a `baseCurrencyAmount`, and it is HMAC-SHA256 signed with `MOONPAY_SECRET_KEY`.

What it does not do is show USDC arriving. There is no balance read anywhere in the file
(`grep -c 'getTokenAccountBalance\|uiAmount'` → 0). The step as written is "we can produce a correct,
signed checkout URL", not "the sandbox path reaches a real USDC balance".

Honest status: the on-ramp *handoff* is proven; the *arrival* is not. On a sandbox that requires a
human to complete a card flow, arrival may not be automatable at all — in which case the step should
be reworded rather than left looking stronger than it is.

## 3. Agent — PASS (execution) / BLOCKED (selection)

**Selection could not run here, and refused correctly.** Driving `runAutonomousCycle` live:

```

```

Cause, measured per symbol rather than assumed:

```
NVDAx  jupiter=218.89  baseRef=null  guard=hold  observations=5
TSLAx  jupiter=364.42  baseRef=null  guard=hold  observations=2
```

The Jupiter price is real. The Base reference price is `null` because this machine has no real
`ONEINCH_API_KEY`, and outside Nasdaq regular hours the off-hours guard holds when it has no second
venue to measure the pool against. That is the guard working as designed, not a defect — but it means
the selection half of step 3 cannot be demonstrated without a 1inch key.

### Defect found and fixed: the agent's fills never reached the position book

On the first run that line read `sleeves NONE`, and the tables agreed: `positions` 0 rows,
`position_sleeves` 0 rows — while the signature was `Confirmed` on chain. `guardAndSpend` places the
swap and returns a receipt; it does not touch `positions`, and nothing on the autonomous path did
either. So an autonomous buy moved real money, wrote an audit row and sent a notification, and then
did not appear in the book at all: Holdings showed nothing, P&L counted nothing, and the sleeve
breakdown had nothing to attribute.

Fixed in `server/src/bot/autonomous.ts`: the cycle now books the fill through `applyFill`, attributed
to `agent` and to the proposal that decided it. A sale books as negative units. Both pinned by tests.

## 4. Fill — PASS, after a fix

**First run failed.** The route reverted and the fill silently degraded to the vault:

```
Program whirLbMiicVdio4qvUfM5KAg6Ct8VwpYzGff3uctyCc success
Program JUP6LkbZbjS1jKKwapdHNy74zcZ3tLUZoi5QNyVTaV4 failed: custom program error: 0x1771
...
FILL PATH   venue-vault — NOT a Jupiter swap
PROOF FAILED: Filled through 'venue-vault' ... no on-chain route executed.
```

`0x1771` is 6001, Jupiter's `SlippageToleranceExceeded`. Note the Whirlpool CPI **succeeded** — the
swap executed and then Jupiter's own output check rejected it.

Cause, measured rather than guessed: the price is a **live mainnet** quote while the fill executes
against **pool accounts cloned at an earlier slot**. They drift. At $100 of NVDAx the cloned pool
delivered `45,664,177` against a 50 bps floor of `45,678,185` — short by roughly three basis points.
So the default 50 bps sits exactly on the edge, and the gap widens the longer a fork runs. Probing
the fill directly:

```
   50 bps -> venue = venue-vault
  200 bps -> venue = jupiter-route
```

Fixed in `server/src/venues/jupiter.ts`: off mainnet only, slippage is floored at 200 bps
(`FORK_MIN_SLIPPAGE_BPS`). This is headroom for a frozen clone, not a trading decision — on mainnet
the quote and the pool *are* the same moment, 50 bps is the real tolerance, and widening it there
would mean accepting a materially worse fill than the one quoted. The file already gated route
pinning the same way.

## 8. Withdraw — FAIL

What genuinely passes: the allowlist and its 24-hour cooling-off (real, database-backed — a new
address reads `cooling_off` and becomes usable only after the window by the database clock), base58
validation, EVM-address rejection on a Solana cluster, and that the **user's** key signs rather than
the executor's.

What does not: the transaction is never broadcast, and could not be.

```ts
// tools/prove-solana-deposit-withdraw.ts:195
tx.recentBlockhash = Keypair.generate().publicKey.toBase58();
```

That is a random public key used as a blockhash. `grep -c 'sendRawTransaction\|sendAndConfirmTransaction'`
over the file returns **0**. The printed "User Transaction Signature" is the signature bytes
hex-encoded, with a `'demo_sig'` fallback — not a base58 signature the chain ever saw.

So step 8 proves *authorisation* and *policy*, and does not prove *settlement*. Not fixed here: it
needs a funded user ATA on the fork, a real blockhash and a broadcast, which is more than a small
change — and a half-fix would leave the tool looking more real than it is, which is the specific
failure this harness exists to prevent.

## Recommended follow-ups

1. **Make step 8 settle.** Fund the user ATA on the fork, use a real blockhash, broadcast, and assert
   the destination balance moved.
2. **Reword step 1**, or automate arrival. As written it proves a signed URL, not a funded wallet.
3. **A 1inch key for demo machines**, or the agent's selection half cannot be shown outside Nasdaq
   regular hours.
4. **Record price observations on a schedule.** NVDAx had 5 and TSLAx 2; the balanced profile needs 6
   before a band counts, so even with the guard clear the range strategies would have stood down.
